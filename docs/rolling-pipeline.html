Lancer Roll Pipeline

What happens between clicking Generate and a token landing in Foundry — the twenty-five draws, the flags that gate them, the one random stream that makes them reproducible, and the round trip the GUI makes back through all of it to change a single trait. Every box below is coloured by the repo that owns it, so the picture answers which file do I open as well as what happens next.

lancer-art-generator — Python: rolls, prompts, renders lancer-npc-import-gui — Node: forms, routes, argv state on disk — tables file, manifest a trap, or two things that must agree

SUMMARY What "rolling" actually is

An NPC is twenty-five draws from twenty-five markdown tables, taken in a fixed order, from a single random stream — plus one more draw for each table whose first draw lands on a => Name group reference, which picks a member of that group. Nothing about that is unusual. The three things worth knowing before reading any of the code are:

Earlier draws gate later ones, through flags carried on the bullet itself. A Role bullet reads a Union marine soldier || mil. The text before the || goes into the prompt; the flags after it are stripped off and turned into plain Python booleans, which the next twenty tables' filters read. There is no rules engine — every gate is an if name == "Weapon" block matching flag strings literally. That is why the order of REQUIRED_TABLES is load-bearing, and why an unrecognised flag fails silently rather than loudly.

A single-trait re-roll is a whole fresh roll with everything else pinned. There is no code path that patches one value. Re-rolling a Hair runs roll_npc() again with the other twenty-four bullets forced in as overrides — which is the only way the filters can run at all, since a pinned trait is never drawn and therefore never filtered.

The manifest entry is the accumulator. There is no pending-edit map anywhere in the GUI. Each edit reads what the last edit wrote, so a run of changes composes by construction, and the flag artStale is what records that the stored traits and the stored image have parted company.

STAGE 01 Getting in

Four ways a roll starts, and they converge on the same function.

  1. 1.1

    A fresh batch

    --count N with an optional --seed. NPC n of the batch rolls on base_seed + n. Absent a seed, one is drawn from random.randint(0, 2**32-1) and recorded, so any batch is repeatable after the fact.

    generate-npc.py:main POST /api/create-npc → lib/kinds.js:npc.createArgs
  2. 1.2

    A forced trait

    --set-trait Table=value, repeatable once per table. The value is taken verbatim, flags and all — a field medic || civ, not a field medic. Drop the flags and the twenty tables downstream stop seeing the constraint, which is why the Create form's dropdown puts the raw bullet in the option's value and prettifies only its label.

    generate-npc.py:parse_args public/app.js:renderOverrideRows
  3. 1.3

    A re-roll of one trait on an NPC that already exists

    --regen-manifest … --regen-id … --reroll-trait TABLE. Loads the stored entry, frees the target and its cascade, pins the rest, and rolls again. See stage 05.

    generate-npc.py:reroll_from_raw POST /api/stage-trait → lib/applyTrait.js:applyArgs
  4. 1.4

    A read-only question

    --trait-choices TABLE asks what one trait could be on this NPC and what each option would cost; --trait-odds N samples the real roller N times (default 20 000) to report per-bullet frequency. Both print JSON and exit without rendering. Both are cached on the GUI side.

    generate-npc.py:print_trait_choices generate-npc.py:trait_odds lib/traitChoices.js · lib/traitOdds.js
where the GUI learns its vocabulary

At startup the Node server reads each generator script as text and regex-parses REQUIRED_TABLES, REROLLABLE_TRAITS and TRAIT_DEPENDENTS out of the Python source (lib/overrideTables.js, into server.js:OVERRIDE_DATA_BY_KIND). That is deliberate — the alternative is a hand-maintained copy, and the hand-maintained copy is exactly what drifted before: it was missing Weapon, Theme, Height and Hair colour, and still called Glow colour by its old name Accent. Every value it fails to parse degrades to an empty list rather than throwing, so a reformatted Python constant costs you buttons, not a crash.

STAGE 02 The tables

A markdown file, two regexes, and one convention per column count.

## Heading starts a table, - text is one option, and a leading x30 means the option is appended thirty times. There is no weights column: a weight is list repetition, and rng.choice does the rest. Repeating a heading merges the two tables and warns.

The || separator means different things in different tables, and getting it wrong destroys prose rather than failing. Three tables carry three segments — Backdrop is shot || scene || flags, Hair colour is base || tail || flags, Faction is name || visual || flags — and everything else carries two. flags_for(name, bullet) is the one correct way to ask a bullet for its flags; calling split_flags on a Backdrop returns the scene sentence and thinks it is a flag list.

Per-pronoun variants, and the two forms they take

A heading ending in + is additive: ## Outfit (she) + is appended to ## Outfit, so a woman rolls from both pools. A heading without it replaces: ## Build (she) is used instead of ## Build, so with pronouns on "she" every plain Build bullet becomes unrollable. heading_for() is written as the deliberate inverse of variant_table(), in the same order, so a bullet is always attributed back to the heading it would actually have been drawn from.

a convention only the Node side knows

A bullet disabled on the GUI's Tables tab is written back as <!-- - text -->. Python's bullet regex requires a line to start with -, so a disabled bullet is invisible to the roller by construction rather than by agreement. Both regexes have to keep that shape for it to hold.

STAGE 03 Inside roll_npc()

One loop, one RNG, and an accumulator of booleans that grows as it goes.

Soft filters and hard filters

Almost every filter ends options = kept or options: narrow if you can, hand back the original if narrowing emptied the pool. That fallback is what keeps a badly-tagged table from crashing a run, and it is also the source of the trap below.

Four filters deliberately have no fallback — filter_by_role_lock, filter_by_backdrop_role, filter_by_affiliation, and the ship side's filter_by_size — because for those the fallback would hand back precisely what was excluded: gear locked to another job, a scene asserting a job the NPC does not hold, a kilometre-long spinal lance on a one-hex patrol boat.

STAGE 04 Determinism

One stream per NPC. Not one per trait — and that has consequences.

Every table consumes one rng.choice, from the same random.Random(base_seed + n), in REQUIRED_TABLES order — two when that draw lands on a => Name group reference, whose second draw picks the group's member. A file with no groups draws exactly one per table. The same integer is then handed to ComfyUI as the sampler seed for both images. So the value of trait N depends on how many draws preceded it: adding a table, or changing a pool's length, changes every subsequent trait at the same seed.

A forced trait is still drawn and the draw discarded, precisely so that forcing one trait does not shift the stream and change every NPC after it in the batch. The exception is unavoidable — a forced trait that filters a later pool changes that pool's length, and a shorter pool draws differently. So is a forced trait whose discarded draw was a group reference: the member draw is skipped, and the stream after it moves by one.

STAGE 05 The GUI round trip

Every edit is: ask the generator, show the answer, send the choice back, re-read the entry.

  1. 5.1

    Ask what the trait could be

    GET /api/trait-choices spawns --trait-choices TABLE. The generator answers legality by reading back probe[name] — the pool the roller actually built — rather than recomputing it, so there is nothing for it to drift from. It answers cost by re-rolling with each candidate forced and checking whether each dependent's stored bullet survives.

    generate-npc.py:trait_choices lib/traitChoices.js:parseChoicesOutput
  2. 5.2

    Draw the offer behind the same gates that accept it

    The Set… button is drawn behind rerollableFor(item) and hasRawTraits(item) — the identical test the route uses to accept or refuse. A button that answers 400 is worse than no button.

    public/app.js:openSetTrait server.js:rerollableFor
  3. 5.3

    Name the cascade before spending it

    rerollNeedsConfirm asks the dependents map, not either re-rollable list — asked of the lists, Faction, Weather and Stance would open a dialog announcing a cascade that does not exist and be unable to name a single trait. traitCascade() in app.js is a worklist mirror of the Python closure, ordered by overrideTables so it reads the same as the CLI's own report.

    public/app.js:traitCascade generate-npc.py:trait_cascade
  4. 5.4

    Apply without rendering

    POST /api/stage-trait spawns --apply-only: the re-roll runs, the manifest is rewritten, artStale is set, and the new traits are printed on stdout as JSON while every diagnostic goes to stderr. The server keeps that stderr and returns it as the log, from which the client regexes out the "…with Hair colour: 'x' → 'y'" lines to say what else moved. Rendering stays on the separate Regenerate button.

    server.js:runApplyTrait generate-npc.py:regenerate_one
  5. 5.5

    Re-read rather than echo

    The server re-reads the manifest entry instead of forwarding the generator's stdout: the generator's stdout says what it rolled, and the entry says what is stored. Those are different claims, and only the second is what the next click will read.

    .generated-npcs.json

STAGE 06 Spaceships

The same roller with the pronoun axis swapped for a size axis.

generate-spaceship.py imports generate-npc.py by path and binds nineteen names to module-level aliases — parse_tables, variant_table, every splitter, the theme filters, filter_by_mil, the glow machinery — so that an NPC-side rename fails in test/test_shared_surface.py rather than at render time. The single cleverest reuse is variant_table(): it takes a caller-supplied string and does not care what it means, so ## Hull (huge) and ## Outfit (she) + work through identical code with zero change on the NPC side.

REFERENCE Where to modify what

The question this page exists to answer at a glance.

To change…OpenAnd know that
An option's wording, weight or on/off state prompts/npc-generator-tables.md No code change. The GUI's Tables tab edits this file in place.

REFERENCE Where two implementations must agree

Ranked by how quietly each one fails.

  1. 01

    A Node process regex-parsing a Python file

    lib/overrideTables.js reads REQUIRED_TABLES, REROLLABLE_TRAITS, RAW_REROLLABLE_TRAITS and TRAIT_DEPENDENTS out of the generator's source text. Reformatting a constant empties a list, silently. Three mitigations are load-bearing: every parse degrades to empty rather than throwing; the ^ anchor is the only thing separating REROLLABLE_TRAITS from RAW_REROLLABLE_TRAITS, which contains it as a substring; and the empty-exclusion check in rawRerollableTraitsFrom exists because without it an unreadable not in (…) returns the whole of REQUIRED_TABLES — the one wrong answer with a plausible shape.

  2. 02

    The flag vocabulary against the tables themselves

    The generator matches flags literally and ignores anything it does not recognise, so || Figure or || hand fails only in the finished image. That is the entire argument for a checkbox per known flag rather than a text box. tableFlags.test.js's "every flag the live tables use has a checkbox" is what holds the two in step. It once reported six flags without one — Faction's unaffiliated and the five Glow placement prop gates — which are now documented and checkboxed. It skips entirely when no generator sits beside the repo, so a green run elsewhere is not evidence the drift is gone; two hermetic tests beside it pin those six by name as a backstop.

  3. 03

    THREE_SEGMENT_TABLES against flags_for

    Both must list Backdrop, Hair colour and Faction. If flags_for's branch list grows, this grows with it, or the editor writes a flag over a scene sentence.

  4. 04

    TRAIT_DEPENDENTS against the filters it describes

    The map asserts constraints; nothing checks that the filter it names still exists or still reads that flag. This is why every edge carries its own prose justification — the justification is the only re-checkable artefact.

  5. 05

    rawTraits against traits

    reroll_from_raw replaces the NPC wholesale, _raw included, precisely so the two cannot disagree. There was a real bug here: gating persistence only on rerolled left --set-trait entries holding new flag registers over old bullets, which is corruption rather than staleness.

  6. 06

    Two things deliberately not reimplemented

    Worth naming because they are the drift risks the design avoided. Odds are sampled through the real roller rather than derived analytically — sampling cannot disagree with the generator because it is the generator. Legality is read out of probe[name], the pool roll_npc already built, so there is nothing for it to drift from. Both lib/traitOdds.js and lib/traitChoices.js open with a paragraph saying that computing either in JavaScript is not negotiable.

UPKEEP Keeping this page true

what invalidates this document

This page is a picture of code, so it goes stale the way code does. The specific things that make a claim above wrong:

The order strip in stage 02 is REQUIRED_TABLES verbatim — reorder or extend that list and the strip is wrong, as is the "twenty-five draws" figure repeated in the summary and stage 04. The loop diagram in stage 03 is the seven steps between variant_table() and the flag strip; a new step, or a filter that moves across the probe line, changes it. The trap diagram is one comment in the Weapon block; if that block is rewritten, check whether the comment still describes it. The cascade example in stage 04 is trait_cascade("Role") — recompute it rather than trusting the list drawn there. The delta table in stage 06 counts nineteen borrowed names, which test/test_shared_surface.py pins.
